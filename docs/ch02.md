# 第 2 章 Prompt 与结构化输出

起点标签 `ch02-start`，参考答案 `ch02-done`。

## 目标

让小模型「听话」，并拿到程序能直接用的结果：

- 系统提示词变成**带变量的模板**：商城名、客服名、服务范围、今天的日期在每次请求时渲染进去；模板按版本存放（`prompts/system-v1.st`、`system-v2.st`），用 `assistant.prompt.version` 切换，v2 加了更严的规则和 few-shot 示例（只用简体中文、不编造订单信息）
- **意图识别**：让模型按 `IntentResult` 的 JSON Schema 输出，Spring AI 直接转成 Java 对象：`intent`（`ORDER_STATUS` / `PRODUCT_INFO` / `AFTER_SALES` / `CHITCHAT` / `OUT_OF_SCOPE` / `UNKNOWN`）、`confidence`、`orderNo`、`skuId`
- **稳**：输出解析不了就带一句更严格的提醒重试一次，还不行兜底为 `UNKNOWN`，绝不把解析异常抛给用户；`confidence` 夹到 [0, 1]，订单号格式不对就丢掉
- **接口**：新增 `POST /api/intent`；`POST /api/chat` 的响应多一个 `intent` 字段；流式接口最先推一个 `intent` 事件。意图是 `OUT_OF_SCOPE` 且把握够大时直接回拒答话术，**不调回答模型**

页面的调试面板已经加了「意图识别」一栏，这章只写后端。

### 提示一：思路

1. 模板文件放在 classpath 上，拼出路径后先判断存不存在；构造器里已经调用了一次 `systemTemplate()`，抛异常就是「启动失败」
2. Spring AI 只在**给了变量**时才渲染模板：变量表为空，`{shopName}` 原样发给模型；给了变量但少一个，渲染时报错。日期要用注入的 `Clock` 取，测试才能固定「今天」；服务器常跑在 UTC，所以时钟按商城时区（`assistant.prompt.zone`）创建
3. `entity()` 背后是 `BeanOutputConverter`：根据 record 生成 JSON Schema，拿到输出后用 Jackson 反序列化。打开「原生结构化输出」后，Schema 作为模型参数交给厂商（Ollama 的 `format`），不再拼进用户消息；不支持的模型自动退回拼进提示词。分类要稳定，温度只在这一次请求里调成 0
4. 区分两类失败：输出不是合法 JSON 是**格式问题**，值得重试；连不上、超时是**服务问题**，重试也没用，原样抛出交给接口返回 503。重试的那次在用户消息后面加一句「只输出 JSON」的提醒
5. 模型输出「结构对了」不等于「内容对了」：录制文件里能看到 0.5b 把没有的字段写成字符串 `"null"`、把 SKU 写成 `"}"`、把 `ABC123` 当订单号。record 不可变，校验后返回一个新对象
6. 拒答只看「把握够大的 `OUT_OF_SCOPE`」：小模型经常判错，错拒一个正常问题比多答一句无关问题代价大
7. 流式接口的意图已经在 Controller 里识别好（先推 `intent` 事件），`answerStream` 只决定后面推什么

## 录制回放

第 1 章的假模型只能验证「我们的代码」，但结构化输出的难点在**真实模型会输出什么**：多一层 Markdown 代码块、字段写成字符串 `"null"`、标签不在枚举里……这些靠手写的假数据想不全。本章引入测试的第二层：用真实模型跑一遍，把原样输出录下来，之后不联网回放。

| 文件 | 作用 |
|------|------|
| `src/test/resources/recordings/intent-cases.json` | 要录制的 12 条用户消息，以及人工标注的期望意图 |
| `src/test/resources/recordings/intent-qwen2.5-0.5b.json`、`intent-qwen2.5-1.5b.json` | 每条消息的每次模型调用：Prompt 指纹、模型原样输出，以及参考实现解析出的 `IntentResult` |
| `IntentReplayTest` | 用 `ReplayChatModel` 按 Prompt 指纹返回录下的输出，断言解析结果和调用次数与录制时一致；顺带打印每个模型的分类准确率 |
| `IntentRecordingIT` | 录制工具，只有设置了 `RECORD_OLLAMA_URL` 才运行，CI 里永远跳过 |

> 后来改了：下面说的 12 条用例、24 条录制、6/12 与 11/12 是 `ch02-done` 时的数字。第 5 章新增意图 `POLICY`、意图提示词换成 `intent-v2.st`，用例加到 16 条，两个模型都重录了：`main` 上是 2 × 16 = 32 条录制，qwen2.5:0.5b 分对 8/16，qwen2.5:1.5b 分对 14/16。

Prompt 指纹是「系统消息 + 用户消息」的哈希：改了意图提示词或用户消息模板，指纹对不上，回放直接报「没有录制」，提醒你重新录制，而不是拿旧输出假装通过。但只改 `IntentResult` 的字段**不会**让指纹变化：走原生结构化输出时 JSON Schema 作为模型参数传给 Ollama，不在消息文本里，所以改了字段要自己记得重新录制。

重新录制（模型服务地址只走环境变量，不会写进录制文件）：

```bash
# bash / Git Bash
RECORD_OLLAMA_URL=http://localhost:11434 RECORD_OLLAMA_MODEL=qwen2.5:0.5b \
  ./mvnw verify -Dtest=none -Dsurefire.failIfNoSpecifiedTests=false -Dit.test=IntentRecordingIT
git diff src/test/resources/recordings     # 看看模型的输出变了什么
```

```powershell
# PowerShell
$env:RECORD_OLLAMA_URL = "http://localhost:11434"; $env:RECORD_OLLAMA_MODEL = "qwen2.5:1.5b"
.\mvnw.cmd verify "-Dtest=none" "-Dsurefire.failIfNoSpecifiedTests=false" "-Dit.test=IntentRecordingIT"
```

录制时 temperature 为 0，同一个模型、同一版 Ollama 连续录几次结果一致。现有录制的准确率（`IntentReplayTest` 的日志里也有）：qwen2.5:0.5b 分对 6/12，qwen2.5:1.5b 分对 11/12。

## 验收标准

`./mvnw verify` 通过，即下面这些测试全部变绿（start 时它们是红的）：

- `AssistantPromptsTest`：按版本选模板、版本不存在启动失败、变量含商城名 / 服务范围 / 按商城时区的今天、渲染后没有占位符、v2 含更严的规则与示例、拒答话术

- `IntentServiceTest`：解析合法 JSON、Schema 交给厂商且温度为 0、不支持原生时格式说明拼进用户消息、容忍 Markdown 代码块、乱码重试一次后兜底 `UNKNOWN`（恰好 2 次调用）、第二次成功、结果经过校验、未知标签不重试、模型不可用不吞异常
- `IntentApiTest`：`/api/intent` 返回结构化结果 / 乱码兜底 200 / 不可用 503；`/api/chat` 带 `intent`、`OUT_OF_SCOPE` 拒答且不调回答模型、把握不够照常回答；流式先推 `intent`、拒答只推一段、识别失败推 `error`

- `OllamaChatIT`（需要 Docker，本机没有会自动跳过；CI 上会真实执行）：真实 Ollama + `qwen2.5:0.5b`，任意消息都得到合法的 `IntentResult`（不报错），「我的订单 1849203385720832512 到哪了？」识别为 `ORDER_STATUS`；第 1 章的阻塞与流式用例仍然通过

## 本地运行

和第 1 章一样启动（`.\mvnw.cmd spring-boot:run`，或 IDEA 运行配置「智能客服（本地 Ollama）」），打开 <http://localhost:8088/>，展开底部「调试面板」：

1. 问「我的订单 1849203385720832512 到哪了？」：「意图识别」一栏显示 `ORDER_STATUS（查订单）` 和订单号；v2 提示词下回答不会编造物流状态
2. 问「明天北京天气怎么样」：识别为 `OUT_OF_SCOPE`，直接回拒答话术，几乎瞬间返回（没调回答模型）；换成「帮我写一段 Python 冒泡排序」，0.5b 会错判成 `PRODUCT_INFO`，于是照常回答、还真把代码写出来了
3. 只看意图：

   ```bash
   curl -X POST http://localhost:8088/api/intent -H "Content-Type: application/json" -d '{"message":"这件外套有 XL 码吗"}'
   ```

4. 对比提示词版本：`--assistant.prompt.version=v1` 启动（IDEA 里加到 Program arguments），问「这件外套有 XL 码吗」，v1 常常直接编一句「有的」，v2 会说查不到实时库存

0.5b 的意图识别只分对一半左右，会把售后问题错判成 `OUT_OF_SCOPE` 而拒答。想体验正常效果，`ollama pull qwen2.5:1.5b` 后把 `OLLAMA_CHAT_MODEL` 设成 `qwen2.5:1.5b`；或者把 `assistant.chat.refuse-min-confidence` 调到 `1.1`，相当于关掉拒答短路，只看意图不拒答。

## 想一想

- 0.5b 给出的 `confidence` 几乎永远是 0.9（照抄了提示词里的示例），这个值还能拿来做阈值判断吗？有什么更可靠的「把握」来源（多次采样投票、logprobs、规则兜底）？
- 把 `IntentService` 里的 `useProviderStructuredOutput()` 去掉，重新录制 0.5b，看看准确率和输出格式有什么变化；为什么长长的英文 Schema 说明会干扰小模型？
- v2 的系统提示词里放了「今天是…」，而 [Prompt 工程](https://clarence404.github.io/java-doc/ai/1_concepts/1_prompt.html) 建议系统提示词里不要放每次都变的内容以便命中缓存。日期一天才变一次，这个取舍划算吗？换成精确到秒的时间呢？
- 意图识别多花了一次模型调用：在什么情况下值得（拒答省掉的回答调用、第 3 章按意图决定调哪个工具），什么情况下应该把分类和回答合并成一次调用？
- 录制回放断言的是「解析结果和录制时一致」，而不是「分类正确」。为什么？分类对不对应该由谁来管（提示：第 9 章的评估集）
