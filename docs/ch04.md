# 第 4 章 知识入库

起点标签 `ch04-start`，参考答案 `ch04-done`。

## 目标

客服要能回答「七天无理由退货要什么条件」「发票什么时候能开」这类**规则问题**，答案不在商城接口里，而在一堆规则文档里。这一章先把文档变成「可以按意思检索」的知识库；第 5 章 RAG 再把检索结果交给模型回答。

- **知识文档**：`src/main/resources/knowledge/` 下 6 篇虚构的「示例商城」规则（退换货、配送与运费、支付与发票、积分与会员、售后与投诉、账户安全），每篇带 front matter（标题、版本、更新日期），内容具体到天数、金额和例外情况
- **入库流水线**：读 Markdown → 先按标题分节、超长的节再按长度切块（带重叠）→ 每块带上元数据（来源文件、标题路径、序号、内容哈希、文档版本、向量模型名）→ 向量模型把每块变成向量 → 写进向量库
- **幂等增量**：按文档内容哈希判断，没变的跳过（不调模型），变了的先按来源删掉旧块再写新块，删掉的文档也清掉；返回入库报告（新增 / 更新 / 跳过 / 删除的文档数、块数、耗时）
- **两种向量库**：默认 `memory`（Spring AI 的 SimpleVectorStore，可存成 JSON 文件，**不装 Docker、不配数据库也能跑通**）；可选 `pgvector`（PostgreSQL + pgvector 扩展，余弦距离、HNSW 索引）
- **两个向量模型**：Ollama 的 `bge-m3`（默认，1024 维，中文好）和 `nomic-embed-text`（768 维，以英文为主、更小）；维度从模型探测，不写死；nomic 要求的查询 / 文档前缀按模型配置
- **调试接口与页面**：`POST /api/knowledge/ingest`、`GET /api/knowledge/search?q=&topK=`（只检索、不回答）、`GET /api/knowledge/stats`；页面最下面多了「知识库」调试区
- **不影响对话**：启动时自动入库一次，向量模型或向量库不可用只打警告，对话照常可用

页面、接口、错误处理、文档读取、两种向量库的存储与统计、启动时入库、配置都已经给好，这章写的是「怎么切、怎么记、怎么增量、怎么写库、怎么检索、怎么配 pgvector、前缀怎么加」。

### 提示一：思路

1. 规则写在 `split` 的 Javadoc 里，一条一条照做。关键是循环：每轮算候选终点 `end`，不是最后一块就在 `[start + maxChars/2, end)` 里往回找断句字符（`lastBoundary` 已写好，返回断句字符之后的位置），然后 `start = end - overlap`；别忘了「至少前进 1」，否则 overlap 很大时会死循环
2. 先 `chunker.chunk(document)` 拿到块，`docHash(document)` 整篇算一次。块文字带上标题路径是为了让向量里有「这一节讲什么」；ID 用 `UUID.nameUUIDFromBytes` 而不是 `randomUUID`，同样的内容每次得到同样的 ID
3. 把库里的汇总按 source 放进 Map，遍历磁盘上的文档分三类；剩下的「库里有、磁盘上没有」就是删除
4. 「更新」不能只 `add`：新版本切出的块少了，按 ID 覆盖会留下多出来的旧块，所以先 `delete(bySource(...))`。全部跳过时不要调 `store.vectorStore()`——它要探测维度，会去连模型
5. `SearchRequest.builder()...similarityThresholdAll()`，`store.vectorStore().similaritySearch(request)`；`Document#getScore()` 两种库都已经是余弦相似度
6. Hikari 默认在创建连接池时就连一次数据库，连不上直接抛异常，整个应用起不来；`initializationFailTimeout = -1` 推迟到第一次使用。PgVectorStore 是在 `afterPropertiesSet()` 里建表的，它不是 Spring Bean，要自己调
7. 向量库调哪个方法，决定了这段文字是「查询」还是「文档」：`embed(String)` 是查询；`embed(Document)` 与 `getEmbeddingContent(Document)` 是文档。`embed(Document)` 里要调 `delegate.embed(...)`，别调到自己的 `embed(String)`，否则又加上一次查询前缀

## 入库在 Spring AI 2.0 里怎么跑

`VectorStore#add(documents)` 一次做完「向量化 + 存储」：

1. 向量库拿每个 `Document` 的文字调 `EmbeddingModel`，得到一串浮点数（向量）。**SimpleVectorStore 逐块调 `embed(Document)`，一块一次 HTTP 请求；PgVectorStore 批量调 `embed(List<Document>, options, 分批策略)`**，按 token 数分批，一批一次请求
2. 内存版把「ID → 文字、元数据、向量」放进一个 Map；pgvector 执行 `INSERT ... ON CONFLICT (id) DO UPDATE`，每块一行（`id uuid`、`content text`、`metadata json`、`embedding vector(维度)`）
3. 检索时问题也调一次 `embed(String)`。内存版和**每一块**算余弦相似度再排序；pgvector 执行 `ORDER BY embedding <=> ?`（`<=>` 是余弦距离），有 HNSW 索引时不用逐行计算

几处实测出来的细节（和直觉或文档不一致的地方，代码里都处理了）：

- **SimpleVectorStore 列不出全部块**：存块的 Map 是 protected 字段，值类型 `SimpleVectorStoreContent` 在 2.0.2 里是包内可见的，别的包里连类名都写不出来。`MemoryKnowledgeStore` 用一个子类把 Map 露出来，按它实现的公开接口 `Content` 取元数据；`add` 传空列表直接抛 `IllegalArgumentException`；`save(File)` 不建父目录
- **PgVectorStore 探测维度失败时不报错**：没传 `dimensions` 时它自己调模型探测，模型临时连不上就打一行警告、**按 OpenAI 的 1536 维建表**。所以 `PgVectorKnowledgeStore` 自己先探测、失败就报 `EMBEDDING_UNAVAILABLE`，成功了再明确传维度，并且推迟到第一次用到时才建表
- **PgVectorStore 建的 metadata 列是 `json`（不是 `jsonb`）**，插入时却写 `?::jsonb`；按条件删除失败时把 SQL 异常包成 `IllegalStateException`，所以 `KnowledgeException.classify` 沿着 cause 链找数据库异常
- **初始化会执行三条 `CREATE EXTENSION`**（`vector`、`hstore`、`uuid-ossp`），用户要有建扩展的权限；`pgvector/pgvector` 镜像里用 `POSTGRES_USER` 建的用户是超级用户
- **相似度阈值的「全部接受」其实是 0**：`similarityThresholdAll()` 设的是 0.0，余弦相似度为负的块两种库都会被过滤掉（真实模型的中文文本很少出现负值）
- **两种库的分数口径一致**：内存版直接算余弦相似度；pgvector 查出余弦距离，换算成 `1 − 距离`。实测同一个模型、同一个问题，两边的分数到第 4 位小数都一样（`PgVectorStoreIT` 也有断言）
- **`EmbeddingModel#getEmbeddingContent` 默认只取 `getText()`**：元数据不会拼进向量化的文字，标题路径要自己写进块文字

## 为什么这么设计

**每个模型一张表 / 一个文件**。向量只有同一个模型生成时才能比较：bge-m3 的第 1 维和 nomic-embed-text 的第 1 维含义完全不同，维度也不一样（1024 / 768），pgvector 的列类型 `vector(1024)` 根本放不下 768 维的向量。可选的做法有两种：一张表 + 发现模型不一致就报错让人重建；或者每个模型各用一张表。本项目选后者（表名 `knowledge_chunk_bge_m3`、`knowledge_chunk_nomic_embed_text`，内存版的 JSON 文件同理）：来回切换模型对比效果时不用每次重建，切回来直接能用。万一手动把两个模型指到了同一张表（`assistant.knowledge.pgvector.table`），入库和检索时会发现维度或元数据里的模型名对不上，返回 409 `INDEX_MODEL_MISMATCH`，提示 `POST /api/knowledge/ingest?rebuild=true`（删表重建）。

**维度不写死**。默认第一次用到时调一次模型看向量多长（Spring AI 的模型类会缓存），也可以用 `assistant.knowledge.dimensions` 指定。不在启动时探测：模型没启动会拖慢启动，而知识库只是辅助功能。

**内容哈希做增量**。哈希 = SHA-256（切块参数 + 文档前缀 + 文件原文），改了切块参数或前缀，文档没变也会重切。比修改时间可靠：git checkout、复制都会改时间。块 ID 是「来源 + 序号 + 哈希」算出的 UUID，同样的内容重复写只会覆盖。

**切块：先按标题、再按长度**。一节讲一件事，按标题切最符合语义；300 字以内一节一块，超长的再切，相邻两块重叠 50 字。块文字带上标题路径，切开的段落（「需同时满足以下条件」）才知道自己在讲什么。

**前缀**。nomic-embed-text 训练时约定查询加 `search_query: `、文档加 `search_document: `，不加效果明显变差；bge-m3 不需要。前缀写在 `application.yml` 的 `assistant.knowledge.model-profiles`，按模型名前缀匹配，只在调模型时加，不存进库里。

## 本地运行

**默认零依赖**：memory 模式不需要 Docker 和数据库，只要 Ollama 上有向量模型：

```bash
ollama pull bge-m3              # 默认的向量模型，约 1.2 GB，1024 维，中文好
ollama pull nomic-embed-text    # 可选，约 270 MB，768 维，以英文为主
```

像前几章一样启动（IDEA「智能客服（本地 Ollama）」，或 `.\mvnw.cmd spring-boot:run`），日志里会看到「知识入库完成：新增 6 … 篇，写入 38 块」。打开 <http://localhost:8088/>，展开最下面的「知识库」：上面一行是概况（库类型、模型、维度、文档数 / 块数），输入问题点「检索」看命中哪些块和分数，「入库」再跑一次增量（勾上「清空重建」就全部重来）。向量存在 `target/knowledge/knowledge_chunk_bge_m3.json`，重启后读回来，文档没变就全部跳过。

**换向量模型**：环境变量 `OLLAMA_EMBEDDING_MODEL=nomic-embed-text`（IDEA 运行配置里已经列出），或在 `application-local.yml` 写 `spring.ai.ollama.embedding.model`。换模型后知识库**必须重新入库**——不同模型的向量不能混用。本项目按模型分表 / 分文件，换过去第一次启动会自动入库到新表（新文件），旧模型的数据原样留着，切回来直接能用。claude-cli / codex-cli 两个 profile 没有向量模型，知识库同样用 Ollama 的向量模型（也是 `OLLAMA_EMBEDDING_MODEL`）；openai profile 用兼容接口的 `/v1/embeddings`（`OPENAI_EMBEDDING_MODEL`，默认 `text-embedding-3-small`；DeepSeek 没有这个接口，入库与检索会返回 503，对话不受影响）。

```sql
\d knowledge_chunk_bge_m3                                   -- embedding vector(1024)，索引 USING hnsw (embedding vector_cosine_ops)
SELECT metadata->>'source', count(*) FROM knowledge_chunk_bge_m3 GROUP BY 1;

```

### 实测：两个模型检索效果对比

共享开发机（仅 CPU）上的 Ollama，6 篇文档切成 38 块，`topK=3`，memory 与 pgvector 的结果和分数完全一致：

| | bge-m3（1024 维） | nomic-embed-text（768 维） |
|---|---|---|
| 首次入库（38 块） | 约 10 秒 | 约 6 秒 |
| 七天无理由退货要什么条件 | ① 适用条件 0.81 ② 不支持七天无理由的商品 ③ 退货运费 | ① 适用条件 0.75 ② 不支持七天无理由的商品 ③ 退货运费 |
| 发票什么时候能开 | ① 发票 > 开票时间 0.77 | ① 配送 > 签收与查件（错），开票时间不在前三 |
| 积分多久过期 | ① 积分有效期 0.81 | ① 会员权益（错），积分有效期不在前三 |
| 被骗了说要我提供验证码 | ① 账户安全 > 防诈骗提醒 0.70 | ① 售后 > 申请售后（错） |
| 东西坏了能退吗 | ① 拒收与退货地址 ② 不支持七天无理由的商品 ③ 退款时效（都在退换货规则里，但「质量问题退换货」没进前三） | 前三名分散在发票、配送、退款时效 |
| how long does shipping take | ① 配送范围与时效 0.65 | ① 发货时效 0.43 |

结论：中文规则用 bge-m3；nomic-embed-text 只有字面重合度高的问题（「七天无理由」）才找得对。注意分数只能在同一个模型内部比较——nomic 的 0.75 不比 bge-m3 的 0.81「差」，两个模型的分数分布不同。「东西坏了能退吗」这种口语化、和原文用词差得远的问题，bge-m3 也只找到了大方向，这正是第 5 章要处理的：多召回几块、改写问题、或者加上关键词检索。

## 想一想

- 切块大小从 300 改成 100 或 1000，「七天无理由退货要什么条件」的检索结果会怎么变？块太小、太大分别丢了什么？
- 增量入库按「整篇文档」判断变没变，改一个字整篇重新向量化。能不能做到按块增量（只重算变了的块）？块的 ID、哈希要怎么设计？
- 为什么检索结果里分数最高的也只有 0.8 左右，而不是接近 1？问题和答案「意思相近」为什么不等于「向量相同」？
- 知识库有 10 万块时，内存版每次检索都要和每一块算一遍；pgvector 的 HNSW 是「近似」最近邻，可能漏掉真正最近的那块。各在什么场景下能接受？
- 现在 `/api/knowledge/ingest` 谁都能调。真实项目里入库会花钱（调云端模型）、会删数据，该怎么保护？文档更新后怎么自动触发入库？
- 第 5 章要把检索结果拼进提示词让模型回答，并标出引用来源。现在每块带的元数据里，哪些会用上？还缺什么？
