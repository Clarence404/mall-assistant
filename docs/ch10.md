# 第 10 章 生产化：共享状态与监控落地

起点标签 `ch10-start`，参考答案 `ch10-done`。第 9 章收尾时列了「离生产还差什么」，头一条是「状态都在一个进程里」，最后一条是「可观测只到能看」——这一章把这两条做掉。

## 目标

第 9 章的保护和监控都是对的，只是两处还停在「单机、纸面」：

1. **起两个实例，规则就变了**。每分钟 20 次变成每个实例 20 次；每日预算变成每个实例一份；并发上限 8 变成 16 压在同一台 Ollama 上；A 实例生成的确认卡片，负载均衡把「确认」转到 B，B 说「不存在」；两个实例同时收到同一个确认，各执行一次——取消两次、两张售后单
2. **监控文件没跑过**。第 9 章写了面板 JSON 和 9 条告警规则，但「本仓库不部署 Prometheus / Grafana」——指标名写错、PromQL 算出空值，谁也不知道

具体做了这些：

- **共享状态抽成接口，两种实现**：对话限流（`RateLimiter`）、并发名额（`ConcurrencyLimiter`）、Token 账（`UsageStore`）、第 8 章 MCP 的次数上限（同一个 `RateLimiter`）、第 7 章的待确认操作（`ConfirmationStore`）、第 6 章「同一会话同时只答一个」的标记（`ConversationLocks`）和「令牌是谁」的缓存（`OwnerCache`）。内存实现就是前几章的数据结构原样挪出来，默认；Redis 实现在新的 `state/` 包里。一个开关切换：`assistant.state.store: memory | redis`
- **原子性**：滑动窗口、分布式信号量、一轮记账各是一段 Lua 脚本；确认的「只执行一次」是一条 `SET NX PX`；会话标记是经典的分布式锁（`SET NX PX` 占、Lua 比较再删除）。每个键都带前缀、都会过期
- **Redis 挂了怎么办**：`assistant.state.on-redis-error: allow | reject`。放行：限流不计数、预算当没用、并发名额退回本实例的信号量；拒绝：503 `STATE_UNAVAILABLE`。待确认操作不听这个开关，一律拒绝（503 `CONFIRMATION_UNAVAILABLE`）。出错一次冷却 5 秒，不让每个请求都等一次超时；每次出错计入 `assistant_state_errors_total`
- **熔断器不共享**：每个实例一份，讲清楚为什么
- **监控真的跑起来**：`monitoring/docker-compose.yml`（Prometheus 3.5.0 + Grafana 11.6.1，版本写死）；Prometheus 用 file_sd 抓应用单独的管理端口；Grafana 通过 provisioning 自动建数据源、加载面板；告警规则有了单元测试（`alerts.test.yml`），CI 里用 `promtool` 跑；面板里两处 PromQL 修正、四个新面板、两条新告警；`MonitoringFilesTest` 保证面板和告警里写的指标名应用真的会输出
- **测试**：同一套契约测试跑两种实现（`MemoryStateContractTest` / `RedisStateContractIT`）；`RedisMultiInstanceIT` 用两个 Redis 客户端模拟两个实例，证明限流、预算、名额、确认真的共享了；`RedisDownTest` / `RedisDownApiTest` 连一个没人监听的端口，测两种策略

要你写的是 Redis 实现里「最核心的那几行」：滑动窗口的脚本、分布式名额的轮询、一轮记账、确认的抢占、分布式锁的占和还、出错时放行还是拒绝。接口、内存实现、装配、Lua 的其余脚本、监控文件、测试都已经给好。

## 共享状态在 Spring 里怎么做

| 积木 | 是什么 | 本章怎么用 |
|---|---|---|
| Spring Data Redis 的 `StringRedisTemplate` | 键、值都按字符串处理的 Redis 客户端外壳，异常统一翻成 Spring 的 `DataAccessException` | 每个 Redis 实现都用它；catch 一种异常就够了 |
| `DefaultRedisScript` + `ResourceScriptSource` | 从 classpath 读一段 Lua；执行时先 `EVALSHA`，Redis 说没见过再 `EVAL` 全文 | `RedisKeys.script("sliding-window.lua", Long.class)`，Lua 的整数回成 `Long` |
| `LettuceConnectionFactory` | Lettuce（基于 Netty）一条连接给所有线程共用，不需要连接池；默认第一次用到才建连接 | `RedisStateConfig` 自己建：命令超时 500 毫秒、连接超时 1 秒、断线立刻拒绝命令 |
| `@ConditionalOnProperty` | 按配置决定哪组 Bean 生效 | `MemoryStateConfig` / `RedisStateConfig` 二选一，和第 4、6、7 章的 `store` 开关一样 |

### 实测踩到的坑

- **不用 Redis 的 Spring Boot Starter**：`spring-boot-starter-data-redis` 会自动配置连接工厂**和 Redis 健康检查**。默认 memory 模式下根本没有 Redis，`/actuator/health` 就成了 DOWN；redis 模式下 Redis 一抖，健康检查 DOWN，编排系统把所有实例摘掉——而我们本来打算「Redis 挂了限流放行、照常服务」。所以只引 `spring-data-redis` + `lettuce-core`，连接自己建（同第 6 章 JDBC 记忆只引非 Starter 模块的做法），`RedisDownApiTest` 断言 Redis 连不上时健康检查是 UP
- **Lettuce 默认把命令攒着等重连**：断线时命令不会立刻失败，而是排队等到命令超时。配 `DisconnectedBehavior.REJECT_COMMANDS` 立刻失败；再加 5 秒冷却（`StateFailures#ensureAvailable`）——一轮对话进门要碰三次 Redis，挂了的时候每次都等超时，用户要白等好几秒
- **Lettuce 7 的 `RedisURI` 没有 `getPassword()` 了**：凭据换成了 `RedisCredentialsProvider`。为了从 `redis://:密码@主机:6379/5` 取出密码和库号，干脆用 JDK 的 `URI` 自己解析（`RedisStateConfig#server`）；日志里只打主机、端口和库号
- **限流窗口跨过了重启**：冒烟时先跑了一轮（被预算挡住），换个配置重启两个实例再跑，第 4 次就 429 了——上一轮的 3 次还在 Redis 的窗口里。内存版重启就清零，Redis 版不会：这正是共享的意义，但调试时会让人以为限流算错了
- **共享 Redis 上的契约测试互相污染**：Token 账按天分键，同一个测试类里几个测试都往「2026-11-05」记账，「合计」把别的测试也加进去了，「用得最多的调用方」也换了人。每个测试用自己的随机后缀，还要用自己的「那一天」
- **mall-infra 的 Redis 是 `allkeys-lfu`**：内存满了会挑不常用的键删掉，不管有没有过期时间。限流窗口被删了顶多多放几次，**待确认操作被删了就是 404**。生产上共享状态要放在 `maxmemory-policy noeviction` 的实例里（满了写入报错，按策略处理，而不是悄悄丢数据），或者和缓存用的 Redis 分开
- **`assistant_guard_rejections_total` 没有 `endpoint` 标签**：第 9 章只给它打了 `reason`，写测试断言时按想当然加了 `endpoint`，没匹配上

## 为什么这么设计

### 哪些状态必须共享

| 状态 | 不共享会怎样 | 共享后 |
|---|---|---|
| 对话 / MCP 每分钟次数 | 上限乘以实例数 | 全部实例合计（Lua 滑动窗口） |
| 每日 Token 预算 | 每个实例一份预算 | 一份账（`HINCRBY` / `ZINCRBY`） |
| 并发名额 | 每个实例各 8 个，同一台模型被压上 8 × N | 合计 8 个（分布式信号量，带租期） |
| 待确认操作 | 换了实例 404；两个实例各执行一次 | 哪个实例都找得到，`SET NX` 抢占保证只执行一次 |
| 「会话正在回答」 | 两个标签页落在两个实例上，同时答、互相覆盖记忆 | 分布式锁 |
| 「令牌是谁」缓存 | 每个实例第一次各问一次商城 | 少问几次——**这一项不共享也对**，只是慢一点 |
| 熔断器 | 每个实例自己判断 | **不共享**，见下 |
| 对话记忆、售后申请单 | — | 第 6、7 章已经可以存 PostgreSQL（`store: jdbc`）：它们是「数据」，要持久、要查询；这里的是「协调用的状态」，短命、要快、要原子，放 Redis |

**为什么一个开关管全部**：这几样要么一起共享、要么一起不共享才说得清。只把确认放进 Redis、限流还在内存里，多实例时一半规则是全局的、一半是每实例的，「现在到底限的是多少」谁也说不清。指标 `assistant_state_store_info{store}` 和告警 `MallAssistantMixedStateStores` 专门抓「有个实例忘了配」。

### 为什么要 Lua 脚本

Redis 是单线程执行命令的，**一条命令**天然原子；但「先删、再数、够了就加」是三条。两个实例同时发：A 数到 19、B 也数到 19，各加一条，变成 21 次。三种办法：

- **一条命令就够的，用一条命令**：抢占确认是「不存在才写」，`SET 键 值 NX PX 毫秒`本身就是原子的；记账的每一个数字都是 `HINCRBY`，加法本身不会丢
- **几步要一起看一起改的，写成 Lua**：Redis 执行脚本时不会插进别的命令。滑动窗口、分布式名额、比较再删除都是这样
- **`MULTI` / `EXEC` 事务**：能保证一组命令连着执行，但中间拿不到前一条的结果（不能「数完再决定加不加」），所以不适合限流；`WATCH` 乐观锁可以，但冲突时要重试，不如脚本直接

**为什么限流不用 `INCR` + `EXPIRE`**：那是固定窗口（每个整分钟一个计数器），简单、一条命令，但 59 秒问 20 次、61 秒再问 20 次，两秒内放行 40 次。第 8 章选滑动窗口就是为了这个，换到 Redis 上算法不变。

**时间用谁的**：脚本里的「现在」由应用传进去，测试可以拨时钟；代价是实例之间的时钟要同步（NTP），偏差多少，窗口就歪多少。不想依赖实例的时钟，可以在脚本里用 Redis 的 `TIME`。

**键里的花括号**：一天的账有六个键，`usage:{2026-11-11}:caller`、`usage:{2026-11-11}:intent`……单机 Redis 里花括号只是普通字符；到了 Redis Cluster，只有花括号里的部分参与分片，这六个键就落在同一个节点上——Lua 脚本要求它碰的键都在同一个节点，否则报 `CROSSSLOT`。现在写上，换集群时不用改。

### 确认只执行一次：抢占，而不是锁

第 7 章每个确认一把 `ReentrantLock`。锁在一个 JVM 里，两个实例各有各的锁，两次点击落在两个实例上就会各执行一次。

最直接的改法是分布式锁：`SET lock NX PX 30000`，执行完删掉。问题在过期时间：锁必须会过期（不然拿锁的实例挂了，这个确认永远锁死），而写操作可能比过期时间还慢（商城卡住了），锁一过期，第二个请求进来再执行一次——正是要防的事。

所以这里是**抢占，不释放**：谁先 `SET confirm:{ID}:claim APPROVE NX` 成功，谁去执行，执行完把结果写进 `confirm:{ID}:outcome`；后来的看到已经有人抢了——决定相同就等结果（每 20 毫秒看一次，最多 10 秒），决定不同就是 409。抢到的实例挂在半路，这个确认就停在「处理中」，用户看到 409 `CONFIRMATION_IN_PROGRESS`，过期后重新提。这是**最多执行一次**：对写操作，办不成比办两次好收拾（第 7 章同样的道理：写操作不重试）。真正「恰好一次」要靠下游配合——把确认 ID 当幂等键传给商城，商城那边去重（mall-evolution 下单接口的 `Idempotency-Key` 就是这个）。

### 会话标记：经典的分布式锁，以及它的边界

「同一会话同时只答一个」用的正是分布式锁，三个要点对应三行代码：`SET 键 令牌 NX PX 租期`（占和过期必须是**一条**命令，分成 `SETNX` + `EXPIRE` 两条，中间挂了就是永不过期的锁）；租期到了自动放开；还的时候比较令牌再删（`unlock.lua`），否则可能删掉别人的锁。

它不是绝对安全的：持有者卡得比租期还久（长 GC），别人照样能进来。对「尽量别两个一起答」够用；真要严格互斥（扣库存），写入那一侧要再查一次版本号（fencing token）。Redisson 的看门狗会自动续期，减少「还没做完锁就过期」，但同样不是绝对的。

### Redis 挂了：放行还是拒绝

| | 放行（allow，默认） | 拒绝（reject） |
|---|---|---|
| 每分钟次数 | 不计数，放行 | 503 `STATE_UNAVAILABLE` |
| 每日预算 | 当作今天还没用 | 503 |
| 并发名额 | 退回本实例的信号量（每实例不超过上限） | 503 |
| 会话标记 | 这一轮不加锁 | 503 `MEMORY_UNAVAILABLE` |
| 记账 | 只记指标（回答已经给出去了） | 同左 |
| 归属缓存 | 当作没缓存，多问一次商城 | 同左 |
| 待确认操作 | **一律拒绝**：生成不了卡片，确认 503 `CONFIRMATION_UNAVAILABLE` | 同左 |

限流和预算是「保护」，不是业务本身：为了保护而让所有人都问不了，等于自己把自己限流到零。本地模型不按量花钱，默认放行。按 Token 付费的模型、或者正在被刷的时候，预算失效就是真金白银，选拒绝。并发名额是例外：本地信号量什么都不依赖，放行时退回它，至少每个实例不超过上限。写操作没得选：「出错就放行」的后果是执行两次。

无论哪种策略，放行期间限流和预算都形同虚设，所以每一次出错都计入 `assistant_state_errors_total{component}`，告警 `MallAssistantStateStoreErrors` 会响。

### 熔断要不要共享

不共享。熔断回答的是「**我**到模型服务这条路通不通」：每个实例到模型的网络、连接池、DNS 可能不一样，A 连不上不代表 B 连不上；共享以后，一个实例的网络抖动会让所有实例一起熔断。代价是每个实例都要自己失败 5 次才熔断（N 个实例就是 5N 次失败），对客服这点量可以接受。Resilience4j、Sentinel 默认也是每实例一个断路器。真要全局「一键熔断」，做成配置中心的开关（人来拍板），而不是让实例互相影响。

### 监控跑起来

**端口与暴露范围**：第 9 章提醒过，`/actuator/prometheus` 和 `/actuator/tokens` 里有用户 ID 和 IP，不能对外。冒烟时用 `management.server.port` 把 Actuator 放到单独的端口（9191 / 9192），对外的 8091 上 `/actuator/prometheus` 是 404，Prometheus 只抓管理端口；生产上这个端口只开给内网和 Prometheus（防火墙或安全组）。不加 `management.server.port` 时 Actuator 和业务同一个端口，`targets` 里就写业务端口。

**抓谁**：`prometheus.yml` 用 file_sd（`targets/*.json`）——改了文件 Prometheus 自己重新读，不用重启，多加一个实例就多一行。仓库里的 `targets/default.json` 指向同一台机器的 8088（`host.docker.internal`，compose 里用 `host-gateway` 让 Linux 也认识这个名字）；应用在别的机器上时，在部署目录里改这个文件（内网地址不进仓库）。

**Grafana 自动加载**：数据源和面板都用 provisioning。第 9 章的面板是「导出给别人 Import」的格式，数据源写成 `${DS_PROMETHEUS}`，Import 时才替换；provisioning 不替换，加载出来每个面板都是「找不到数据源」。改成一个数据源模板变量 `${datasource}`，两种方式都能用。管理员口令只从部署目录的 `.env` 读（`GRAFANA_ADMIN_PASSWORD`，compose 里写成 `${GRAFANA_ADMIN_PASSWORD:?}`，没设就拒绝启动），面板开了匿名只读，不登录也能看。

**面板里的两个 PromQL 问题**（用 Prometheus 的查询接口把 18 个面板的表达式逐个跑了一遍才发现）：

- 「模型错误率」显示 No data 而不是 0%：没有任何 `MODEL_*` 错误时，分子 `sum(rate(...{outcome=~"MODEL_.*"}...))` 是**空向量**（不是 0），空向量除以任何东西还是空。分子补 `or vector(0)`。告警规则里同样的式子不用改：没有错误时本来就不该告警
- 「正在处理的对话」用的是 `max(...)`：多实例时只看得到最忙的那个。改成 `sum by (instance)` 每个实例一条线

另外加了四个面板（各实例每秒请求数、共享状态出错、各实例的存储、抓取状态 up）和一个「实例」筛选变量；两条新告警（`MallAssistantStateStoreErrors`、`MallAssistantMixedStateStores`）。

**告警规则的单元测试**：`promtool check rules` 只查语法——标签名打错、少了 `by`、比较方向反了，语法都是对的，只是永远不响。`alerts.test.yml` 用 `promtool test rules` 造一段假的时间序列，断言某个时刻哪些告警在 firing（实例挂了 45 秒时还没响、2 分钟时响了；错误率一半时响；共享状态出错时响、不再出错 5 分钟后恢复；两个实例存储不一致时响）。CI 里 `verify` 之前跑 `promtool check config` 和 `test rules`，用的是和 compose 同一个 `prom/prometheus:v3.5.0` 镜像。`MonitoringFilesTest` 再从另一头查：面板和告警里写的每个 `assistant_*`，应用真的会输出。

**Alertmanager 没有部署**：告警在 Prometheus 的 Alerts 页面上能看到 pending / firing，但没有发到任何地方。接值班要再起一个 Alertmanager，配钉钉 / 企业微信 / 邮件的接收人和静默规则——那是团队流程的事，这里不做。

## 本地运行

默认 `assistant.state.store=memory`，和第 9 章一模一样，不需要 Redis。

    store: redis

### 实测：真实环境冒烟

本机起两个 ch10-done 的实例（8091 / 8092，管理端口 9191 / 9192，`store=redis`，连共享开发机上 mall-infra 的 Redis 的一个空库，键前缀 `mall-assistant:`；每分钟 5 次、每日预算 3000；共享开发机的 Ollama：qwen2.5:1.5b + bge-m3），Prometheus + Grafana 跑在共享开发机上，商城是本机的 mall-evolution（演示账号，只动它自己新下的一笔订单）：

| 场景 | 结果 |
|---|---|
| 匿名（同一个 IP）在 A、B 上交替问「你好」7 次 | 前 5 次 200（A 3 次、B 2 次），第 6、7 次 429 `RATE_LIMITED`，`Retry-After` 53 秒——两个实例合计 5 次 |
| 登录演示账号，A、B 交替问规则类问题 | A 上一问后两边 `/api/usage/me` 都是 1380 / 3000；B 上一问后两边都是 2741；第三问（A，「退货的运费谁出」登录后走了 Agent）一轮用掉 5182，到 7923（预算按轮检查，最后一轮可能超出很多）；第四问在 B 上 429 `TOKEN_BUDGET_EXCEEDED`，`Retry-After` 到零点 |
| 演示账号新下一笔待支付订单，用 MCP 在 **A** 上 `proposeCancelOrder` | 返回确认 ID 与 A 的确认链接；在 **B** 上 `GET /api/agent/confirmations/{ID}` 是 PENDING |
| A、B **同时** `POST` 确认 | 两边都是 200 EXECUTED、同样的话术（0.54 / 0.57 秒）；A 的日志「确认 …：APPROVE → EXECUTED」，B 的日志「正在由另一个请求处理（APPROVE），等它的结果」「重复提交，返回原来的结果」；商城订单「已取消」，只执行了一次 |
| 之后在 A 上点「取消」 | 409 `CONFIRMATION_ALREADY_DECIDED` |
| 8091 上 `/actuator/prometheus` | 404（Actuator 只在管理端口） |
| Prometheus Targets | 9191、9192 两个都是 up |
| Grafana 面板 | provisioning 自动加载；18 个面板的表达式逐个在 Prometheus 上查：除了「提示注入拦截」「共享状态出错」（冒烟期间没发生）都有数据；修正前「模型错误率」是 No data，修正后 0%；「各实例的共享状态存储」两行都是 redis |
| 停掉 B | 23 秒后 `MallAssistantDown{instance=…:9192}` pending，再过 1 分钟 firing（`for: 1m`）；Grafana「抓取状态」里 B 变成 DOWN |

两个 Redis 集成测试连同一台 Redis 的另一个库跑完，按前缀删干净，库里不留键。

## 想一想

- 放行策略下 Redis 挂了 10 分钟，这 10 分钟里限流和预算都不起作用。如果你用的是按 Token 付费的模型，你会选 reject 吗？有没有「既不完全放行、也不完全拒绝」的做法（比如退回本实例的限流、每个实例分 1/N 的额度）？
- 抢占不释放，抢到的实例挂在半路，确认就永远停在「处理中」。用户看到 409 之后怎么办？要不要有一个后台任务，把「抢占了很久、没有结果」的确认拿去商城查一下真实状态再补上结果？
- 分布式名额靠轮询，不公平：先来的不一定先拿到。高峰时会不会有人一直抢不到？怎么改成排队（提示：有序集合按到达时间排，只放前 N 个）？
- 预算按轮检查，一件 Agent 的事能把 3000 的预算用到 7923。把检查挪到每次模型调用之前（`UsageAdvisor`），共享账以后有什么新问题（两个实例同时检查、同时放行）？
- 熔断器不共享，三个实例要各自失败 5 次。如果模型服务是按调用收费、而且失败也收费，你会改成共享吗？
- 共享状态和缓存放在同一台 `allkeys-lfu` 的 Redis 里，内存满的时候会发生什么？怎么在监控上提前看出来（`evicted_keys`）？
- `MonitoringFilesTest` 只查「指标名存在」，查不出「PromQL 算出空向量」。你会怎么把「面板的每个表达式在有数据的 Prometheus 上都返回结果」也做成自动检查？

## 收尾

第 9 章说「能观测的才能评测，能评测的才敢上线」；这一章补上了「上线之后」：**规则写在代码里，状态放在进程外**——同一份 `ChatGuard`、`ConfirmationService`，接口后面换成 Redis，三个实例就像一个；**监控文件要跑过、要测过**，不然它只是看起来像监控。

还没做的（第 9 章「离生产还差什么」里剩下的）：身份（OAuth 2.1）、更强的模型与分层路由、从线上采样的评测集、知识库审核与权限、模型化的护栏、灰度与 A/B、成本优化、链路追踪的 exporter 与告警接值班（Alertmanager）。
